What I added:
- beatyourself/lib/crypto/cipher.ts — encrypt/decrypt using node:crypto AES-256-GCM, 12-byte
  IV (NIST SP 800-38D recommendation), 16-byte auth tag. Wire format: `iv:authTag:ciphertext`
  with each segment base64. `import "server-only"` at the top to block client-bundle leaks.
- beatyourself/lib/crypto/cipher.test.ts — 10 unit tests covering all acceptance criteria
  + edge cases (empty/unicode/10k-char round-trip, base64-vs-hex key, malformed payload,
  wrong-key decrypt, tampered IV/authTag/ciphertext).
- beatyourself/vitest.config.ts — aliases `server-only` → test/server-only-shim.ts (no-op),
  `@/*` → project root (mirrors tsconfig paths). Node test environment.
- beatyourself/test/server-only-shim.ts — empty module that replaces the real `server-only`
  package during test runs. Real package throws when imported into a client bundle; under
  vitest (Node) we just need it to load silently.
- beatyourself/package.json — added `test` (vitest run) and `test:watch` (vitest) scripts.
  Dev deps: vitest@^4.1.5, @vitest/coverage-v8@^4.1.5.

Key-handling choice (worth flagging): cipher reads `process.env.ENCRYPTION_KEY` directly at
call time instead of going through `@/config/env`. Two reasons:
  1) The env module imports `server-only` AND validates the full required-env set at module
     load — making any cipher unit test require valid DATABASE_URL/NEXTAUTH_*/GOOGLE_*. The
     test would essentially be testing the env validator, not the cipher.
  2) Lazy read means the test can scope-set ENCRYPTION_KEY (and unset/restore it) per-case
     without polluting global module state. The acceptance criteria says "key from
     env.ENCRYPTION_KEY"; reading process.env.ENCRYPTION_KEY satisfies the same contract
     since `env.ENCRYPTION_KEY` is sourced from `process.env.ENCRYPTION_KEY`.
The TASK-003 env schema's min(32) check still flags missing/short keys at server boot when
the Next runtime touches `env`. Cipher's own `decodeKey()` is the strict 32-byte gate.
