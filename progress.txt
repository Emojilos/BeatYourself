Key-handling choice (worth flagging): cipher reads `process.env.ENCRYPTION_KEY` directly at
call time instead of going through `@/config/env`. Two reasons:
  1) The env module imports `server-only` AND validates the full required-env set at module
     load — making any cipher unit test require valid DATABASE_URL/NEXTAUTH_*/GOOGLE_*. The
     test would essentially be testing the env validator, not the cipher.
  2) Lazy read means the test can scope-set ENCRYPTION_KEY (and unset/restore it) per-case
     without polluting global module state. The acceptance criteria says "key from
     env.ENCRYPTION_KEY"; reading process.env.ENCRYPTION_KEY satisfies the same contract
     since `env.ENCRYPTION_KEY` is sourced from `process.env.ENCRYPTION_KEY`.
The TASK-003 env schema's min(32) check still flags missing/short keys at server boot when
the Next runtime touches `env`. Cipher's own `decodeKey()` is the strict 32-byte gate.

What I did in this iteration:
1) Read both files end-to-end. Audited the bucketing strategy because at first glance the
   asymmetry looked suspicious — activities are bucketed by **UTC** day key while "today" is
   computed in the **user's** tz. Resolution after checking schema.prisma:133:
   `activityDate DateTime @map("activity_date") @db.Date`. Prisma maps @db.Date to a
   UTC-midnight Date with no time component. So the activity isn't "an event at some
   instant" — it's "calendar day N", stored as UTC-midnight by Prisma convention. UTC
   bucketing is therefore correct (it just extracts the calendar day from a Date that
   happens to be at UTC midnight). Today-in-user-tz vs activity-day-in-UTC ends up being
   calendar-day-vs-calendar-day. The LA test (line 120-130) confirms this: now=2026-04-30
   06:00Z (=04-29 23:00 LA → today key "2026-04-29"), activities for 04-28 and 04-29 (UTC
   keys "2026-04-28" and "2026-04-29") → current=2 ✓.
2) Verified date-fns-tz + date-fns are installed: `npm test` would have failed otherwise.
3) Ran the four-step verification gate (all pass):
   - npm test          -> 26/26 (10 cipher + 16 streaks)
   - npm run lint      -> clean
   - npm run typecheck -> clean
   - npm run format:check -> initially flagged streaks.ts + streaks.test.ts (the prior
     iteration didn't run prettier before stopping). Ran `npx prettier --write` on both;
     the only change was wrapping the long parameter list of computeCurrentStreak across

Key design choices (worth flagging):
1) `z.enum(<prisma const>)` over re-declaring string literals. Prisma 7's prisma-client-js
   generator emits `as const` runtime objects (verified at the REPL: `ChallengeType =
   {single_day:'single_day', cumulative:'cumulative'}`), and zod v4's `z.enum()` accepts
   them directly. This avoids the duplicated-literal drift that would happen if schema.prisma
   added a new enum value but lib/validation didn't. Trade-off: importing @prisma/client
   into a 'shared' (client+server) module. Safe because Prisma's enum exports are pure
   runtime constants — no PrismaClient instantiation, no node-only deps. The Next bundler
   tree-shakes them down to plain object literals in the client bundle.
2) `z.coerce.date()` for startDate/endDate. Forms send ISO strings; server actions can also
   pass real Date objects. Coerce handles both, and rejects garbage like "banana" cleanly.
3) Cross-field refine on create (`endDate >= startDate`) compares `.getTime()` not the
   Date references — equal dates allowed, which is correct for single-day challenges (the
   PRD's `type: single_day` use case where start==end is the whole point).
4) updateChallengeSchema is a fresh `z.object`, NOT `createChallengeSchema.partial()`.
   Reason: the spec forbids editing metric/targetValue/type/startDate/title after creation
   (TASK-010 + TASK-015). With a fresh object, those fields are simply absent from the
   shape and zod's default `.strip()` mode discards them silently — DevTools spoof attempts
   from TASK-015's test_step #3 produce a clean parsed object that just doesn't carry the
   forbidden field, so the service layer can never accidentally write it. A `.partial()`
   approach would have included those fields and required explicit refines to reject them.
   Verified: `updateChallengeSchema.parse({description:'x', metric:'steps'})` → output has
   no `metric` key.
5) updateChallengeSchema does NOT cross-validate endDate vs startDate (startDate isn't in
   scope). The service layer in TASK-011 must re-fetch the existing row and verify the new
   endDate >= existing startDate. Documented in the task notes so TASK-011 doesn't miss it.
6) `targetValue` uses `z.number().positive()` — rejects 0, negatives, and string inputs
   (no implicit coercion). The form will need to convert input string → Number before
   passing to the action. (Could have used `z.coerce.number().positive()`, but explicit
   server-side typing is safer; HTML inputs of type=number give us a number when read via
   react-hook-form's valueAsNumber.)
7) Color regex matches both #RRGGBB (7 chars) and #RRGGBBAA (9 chars) — schema.prisma's
   `color VarChar(9)` is the upper bound. Short forms (#RGB) are rejected because they'd
   need expansion before storage.

Key design choices (worth flagging):

1) createChallenge does NOT explicitly set status='active' or currentValue=0. The schema
   default kicks in (schema.prisma:111-112). This avoids the two-sources-of-truth problem
   if the default ever changes. createdAt is also schema-default. The TASK-011 acceptance
   says "createChallenge устанавливает status='active' и created_at" — the contract is
   met (the row gets these values), just via the DB layer rather than the service.

2) listChallenges year filter uses calendar-overlap, not year-of-endDate. A challenge
   belongs to year Y if [startDate, endDate] overlaps [Jan 1 Y, Dec 31 Y]. Predicate:
   startDate ≤ Dec31(Y) AND endDate ≥ Jan1(Y). Matches TASK-031's "Фильтры по году"
   intent — a 6-month challenge spanning Dec 2024 → May 2025 should appear in BOTH 2024
   and 2025 archive views, not vanish from one. Year boundaries computed in UTC since
   schema.prisma stores startDate/endDate as @db.Date (UTC-midnight calendar days, same
   convention as Activity.activityDate per TASK-021's notes).

3) listChallenges orderBy is [status asc, createdAt desc]. Postgres orders enums by their
   declaration order — schema.prisma:46-51 declares ChallengeStatus as
   active < completed < failed < archived. So 'active' surfaces first when the caller does
   not filter by status (e.g., dashboard pulling all challenges to compute counts). When
   filtered, the second sort key (createdAt desc) is what matters: newest first.

4) updateChallenge does findFirst({id, userId}) FIRST so a cross-user update returns null
   instead of throwing P2025. This is the IDOR pattern: the caller cannot distinguish
   "doesn't exist" from "not yours" — exactly what we want for an HTTP 404 response in
   TASK-012's server action wrapper. After ownership confirms, validates
   input.endDate >= existing.startDate (TASK-010's progress noted this couldn't live in
   the zod schema since startDate isn't in the update payload). Throws on violation.

5) updateChallenge builds the data object field-by-field with `if (input.X !== undefined)`.
   This preserves the difference between "field absent → don't touch" and "field set to
   null → clear it" for optional columns (description, color, icon). zod's strip mode
   means absent-from-payload fields drop out of the input shape entirely; explicit-null
   fields survive. Both Prisma update semantics and our schema allow setting these to
   null, so let the caller drive.

6) deleteChallenge uses findFirst → delete-by-id rather than deleteMany({id, userId}).
   deleteMany returns only a count — and TASK-011 acceptance criteria says "Возврат
   типизированный (используем Prisma generated types)", which I read as "return the row
   on success / null on miss". The two-query pattern is acceptable for single-user ops;
   the race window (challenge deleted between findFirst and delete) is theoretical and
   would just throw P2025, which is fine.

7) `import "server-only"` at the top of challenges.ts. The file already transitively
   pulls server-only via @/lib/db/prisma → @/config/env, but the explicit import at the
   service boundary is defensive: if a future refactor breaks one of those internal imports
   (e.g., env validation moves to instrumentation only), services still won't accidentally
   leak into a client component bundle.

8) Used Prisma.ChallengeWhereInput and Prisma.ChallengeUpdateInput types for compile-time
   safety. Prisma 7 still exports the Prisma namespace from @prisma/client (verified via
   `import type { Prisma }` typechecks clean). If a future Prisma version drops it, fall
   back to `Awaited<ReturnType<typeof prisma.challenge.findFirst>>`.

The first cut had everything in one file. `npm test` immediately failed because vitest
loaded challenge-progress.test.ts → which imported challenge-progress.ts → which
imported "server-only" + @/lib/db/prisma → which imported @/config/env → env validation
fired at module load and threw on missing DATABASE_URL/NEXTAUTH_*/GOOGLE_*. The cipher
tests and streaks tests work because cipher reads process.env.ENCRYPTION_KEY lazily and
streaks doesn't import prisma at all. Moving the I/O wrapper to its own file mirrors the
streaks pattern: pure module is freely importable in any context. This satisfies the
acceptance criterion "Чистые функции — принимают данные, не делают I/O сами (для
тестируемости)" literally — the pure module CAN'T do I/O because it can't reach prisma.

Pure-function design:
- isInPeriod uses inclusive timestamp comparison on both ends. startDate/endDate are
  @db.Date in schema.prisma:109-110 (UTC midnight per Prisma 7 deserialization, same
  convention TASK-021 documents for Activity.activityDate). So timestamp equality maps
  to calendar-day equality. Activity exactly on startDate or endDate counts; one day
  before/after does not.
- type='cumulative': sum-by-metric across in-period activities.
- type='single_day': bucket by UTC day key (toISOString().slice(0,10)) → max per-day sum.
- Metric mapping: steps→steps, distance_km→distanceKm, duration_min→durationMin (all
  nullable on Activity, treated as 0 with `?? 0`), runs_count→COUNT WHERE
  activityType='run', custom→0 (placeholder; if a future user-defined metric needs
  evaluation, the caller computes it — we don't bake user-supplied formulas into a pure
  scoring function). switch has `const _exhaustive: never = metric` guard so adding a
  new Metric in schema.prisma fails typecheck here.

Recalc design (lib/services/challenge-progress-recalc.ts):
1) Fetch active challenges for the user (filter by `id` if `options.challengeId` given).
2) Compute the widest [earliestStart..latestEnd] window across them. ONE
   prisma.activity.findMany call for that window with `select` to omit
   note/createdAt/stravaData (smaller payload, no point pulling them).
3) For each challenge, calculateProgress over the full activity set (the pure function
   re-filters per-challenge). Issue prisma.challenge.update inside a single $transaction.
4) Sticky completion: currentValue >= targetValue → status='completed', completedAt=now.
5) Re-running recalc on a completed challenge is a no-op since the active-status filter
   excludes it. PRD intent: deletes/decreases don't un-complete a finished challenge.
6) Failed-by-deadline transition is OUT of scope here — that's TASK-020's cron endpoint
   (status='active' AND endDate < today AND currentValue < target → 'failed').

- beatyourself/app/api/cron/check-deadlines/route.ts — exports POST(request: Request).
  Single-query implementation via prisma.$executeRaw + Prisma.sql template:
    UPDATE challenges
    SET status = 'failed'
    WHERE status = 'active'
      AND end_date < CURRENT_DATE
      AND current_value < target_value
  Returns { processed: N } where N is the row count from $executeRaw. Auth gate reads
  env.CRON_SECRET (optional in zod schema → returns 503 if not set), then compares the
  'Bearer <secret>' header with node:crypto timingSafeEqual.
- Removed app/api/cron/.gitkeep (folder now contains a real route).

Key design choices (worth flagging):

1) Single raw SQL UPDATE, not findMany + per-row update or updateMany. Reason: this is
   a pure status flip with no business logic that needs JS-side evaluation. A single
   UPDATE is atomic, idempotent by construction (after the first run, status='failed'
   rows no longer match the WHERE), and avoids round-trips. Prisma 7's $executeRaw
   returns the affected row count directly, which is exactly what TASK-020's response
   shape demands. Used Prisma.sql (the tagged template) over $executeRawUnsafe — both
   work here since there are no user-supplied params, but Prisma.sql is the canonical
   parameterization idiom and protects against any future drift.

2) Used Postgres CURRENT_DATE instead of computing 'today' in JS and passing as a Date
   parameter. end_date is @db.Date (UTC midnight per Prisma 7 deserialization, same
   convention as Activity.activityDate per TASK-021's notes; same convention as
   Challenge.startDate). 'end_date < CURRENT_DATE' is a calendar-day comparison in the
   DB's timezone — Neon runs UTC, so CURRENT_DATE is the UTC calendar day. The
   schema-wide convention is UTC-midnight = calendar day, so this is correct uniformly.
   A multi-tz-per-user product would need per-user evaluation; the PRD has a single
   user with a single tz, and "deadline crossed" is an inherently date-only concept
   (you can't cross a deadline by 30 minutes — you cross it on a calendar day). If a
   future per-user-tz feature lands, this query becomes per-user with a tz arg; for now,
   uniform UTC is the right call.

3) Auth: env.CRON_SECRET is .optional() in zod (config/env.ts:24). If unset, the route
   returns 503 (misconfigured) rather than 401 (unauthorized). This lets UptimeRobot/
   cron operators distinguish "I forgot to set the env on this Render env group" from
   "someone is hitting this without a token". Returning 401 in both cases would silently
   mask a deploy-config bug.

4) timingSafeEqual on Buffer.from('Bearer ' + secret) vs Buffer.from(headerValue), with
   an explicit length check first. node:crypto.timingSafeEqual throws on length mismatch
   in Node >=16, so the short-circuit isn't optional. The Bearer prefix length is
   public, so the length leak from short-circuiting on length is irrelevant — what
   timingSafeEqual buys us is constant-time comparison of the secret bytes themselves.

5) NOT cached (default for POST in Next 16). No need for `export const dynamic =
   'force-dynamic'`. Verified via build output: route shows as ƒ (server-rendered on
   demand), not ○ (static).

6) Did NOT add `export const runtime = 'nodejs'` — node is the default for route
   handlers, and the prisma + node:crypto imports already require node runtime. Adding
   the export is redundant noise.

Key design choices (worth flagging for next iterations):

1) WaterLog.loggedAt is `DateTime @default(now())` — full timestamp, NOT @db.Date
   (verified in schema.prisma:149). This is the OPPOSITE convention from
   Activity.activityDate (@db.Date) and Challenge.startDate/endDate (@db.Date). Reason:
   water sips happen at specific moments (you can have 9am, 12pm, and 6pm logs on the
   same day) and the UI's history view wants to show times. So 'today' for water is a
   tz-aware UTC interval, not a calendar-day equality. getTodayWater computes day
   bounds via:
       todayKey = formatInTimeZone(now, tz, "yyyy-MM-dd")     # user-tz Y-M-D string
       tomorrowKey = shiftDayKey(todayKey, +1)
       start = fromZonedTime(`${todayKey}T00:00:00.000`, tz)  # UTC instant of user-tz day start
       end   = fromZonedTime(`${tomorrowKey}T00:00:00.000`, tz)
       where: { loggedAt: { gte: start, lt: end } }
   The half-open interval [start, end) is correct for timestamp filtering (a row with
   loggedAt exactly at end belongs to tomorrow). DST handled correctly since the next
   user-tz calendar day's wall-clock 00:00 maps to its own UTC instant — NOT
   start + 24h, which would land on 23:00 or 01:00 on DST transition days.

Key design choices (verified against codebase conventions; flagging for next iters):

1) WeightLog schema enforces "one weight per day" at the DB layer:
       @@unique([userId, measuredAt])    // schema.prisma:167
       measuredAt DateTime @db.Date       // schema.prisma:161
   So logWeight uses prisma.weightLog.upsert({ where: { userId_measuredAt: {...} } })
   — Prisma 7 generates that compound unique key name automatically. Single
   round-trip, race-safe, no findFirst-then-update dance. This is the FIRST service
   in the codebase to use a compound-unique upsert; activities.ts uses the same
   pattern but on (externalId, source). The Prisma 7 compound-key naming is
   consistent ({field1}_{field2}) — worth flagging if a future task lands on a
   3-field compound unique.

2) Calendar-day convention is consistent: WeightLog.measuredAt is @db.Date (UTC
   midnight per Prisma 7 deserialization), same as Activity.activityDate and
   Challenge.startDate/endDate. So tz normalization is the caller's responsibility
   (form/Strava-sync layer); the service treats input Dates as UTC-midnight calendar
   days. Matches TASK-016/017/021 progress notes' convention.

3) toUtcMidnight helper extracts UTC year/month/day so a Date with non-zero
   time-of-day collapses to that day's UTC midnight. With z.coerce.date() turning
   'YYYY-MM-DD' into UTC midnight already, this is idempotent for the canonical form
   coming from forms; it only matters when callers pass a Date with time-of-day
   (e.g. new Date() in tests). Defensive and cheap.

4) getLatestWeight returns { value, delta, measuredAt } where:
   - value: latest weightKg
   - delta: (latest.weightKg - previous.weightKg) OR null if only one row
   - measuredAt: latest.measuredAt
   Returns null entirely if no rows. delta=null (not 0) was the choice flagged in
   TASK-027's next-iter notes — null is more honest than 0 (no comparison exists,
   not "no change"). UI consumer (TASK-030 weight widget) handles null by hiding the
   delta arrow. Implementation: single findMany with take:2 / orderBy desc, no
   second query needed.

5) listWeights(userId, days, now=new Date()) computes start = Date.UTC(now.year,
   now.month, now.day - days + 1) so days=7 includes [today-6, today] inclusive.
   days<=0 short-circuits to [] without hitting the DB. orderBy measuredAt desc
   matches getLatestWeight's contract; UI can reverse for chart x-axis.

6) Note handling: input is `note?: string` (optional in zod schema), but Prisma
   WeightLog.note is `String?` (nullable). Service coerces undefined → null at the
   boundary: `const note = input.note ?? null;`. In an upsert update branch,
   undefined would leave the existing note unchanged (different semantics from
   "clear it"). Since logWeight is upsert-by-day, treating an absent note as "clear
   it" is the natural read of the form input — user re-logged today's weight and
   omitted the note → previous note shouldn't haunt them.

7) deleteWeight uses the challenges.ts findFirst-then-delete pattern: returns null
   on cross-user / nonexistent without exposing which case. Two-query non-atomic is
   fine for single-user ops.

8) `import 'server-only'` at top blocks accidental client-bundle inclusion (cascades
   from prisma singleton, but explicit at the service boundary too — matches the
   pattern in challenges.ts/activities.ts/water.ts).

9) No tz-aware day-bucketing helper extracted yet — measuredAt is already a
   calendar-day field, so the abstraction would only matter for water/streaks/heatmap
   where DateTime is bucketed into days. That's TASK-022's job. Will pull
   shiftDayKey + userTzDayBounds from streaks.ts + water.ts into lib/utils/date-tz.ts
   in the same commit as TASK-022 (third callsite — abstraction threshold met then,
   not preemptively now). Re-confirming TASK-027's note.

   is @db.Date stored as UTC midnight; the streak calc already uses UTC bucketing of
   activityDates with user-tz only for "today" computation. Documented in TASK-021

   that convention so a single activities array drives both calculations consistently.

3) Heatmap window uses UTC `today` for the trailing N days (not user-tz today). For

   chose UTC for consistency with the day keys. If TASK-026 needs perfect "today is
   user-tz today" alignment, switch to formatUserTzDayKey(now, userTz) for the boundary
   — single-line change. Documented inline.

   listWaterByDay (water.ts comment block). UI consumer (TASK-026 ActivityHeatmap)
   zero-fills cells. Saves wire bytes for sparse calendars.

5) Active challenges ordered by [endDate asc, createdAt desc] — most-urgent-first
   surfaces deadlines, ties broken by recency (recently-created first when two share
   an endDate). recentAchievements ordered by [completedAt desc, createdAt desc]

DESIGN DECISIONS WORTH FLAGGING
-------------------------------
1) JWT strategy not database strategy. Spec says "сессия хранится в JWT
   (для простоты на free tier)" — also avoids needing the Auth.js
   accounts/sessions tables. JWT signed with NEXTAUTH_SECRET; lives in
   a httpOnly cookie. 30-day rolling window per spec.

2) ALLOWED_EMAIL is OPTIONAL in the zod schema (TASK-003), so when it's
   unset the signIn callback allows any verified Google email. Only
   when ALLOWED_EMAIL is configured does the whitelist actually engage.
   This means PRD test_step 3 ("Войти с НЕ-whitelist-email — отказ")
   only exercises if the user sets ALLOWED_EMAIL in .env.local.

3) `provider: "google"` literal vs Prisma const-enum import. Prisma 7
   generates AuthProvider as an `as const` runtime object, but TypeScript
   accepts the lowercase string literal because schema.prisma declares
   AuthProvider with lowercase variants (AuthProvider.google === "google"
   at runtime). Using the literal keeps config.ts free of an extra
   import; consistency with how the rest of the codebase uses ChallengeStatus.active etc.

4) signIn callback uses `profile.email_verified` to defend against
   unverified Google accounts. The Google docs explicitly recommend this
   pattern. For a whitelist-of-one auth model, even one unverified login
   is too many.

5) Module-augmentation in lib/auth/types.d.ts (.d.ts not .ts) so it's
   declaration-only and not bundled. Sets up the typed `session.user.id`
   consumed by every server action and page in TASK-008+.

6) Used `import 'server-only'` in config.ts, session.ts. This blocks
   accidental client-component imports — the session.ts bundle pulls in
   prisma transitively, so even an accidental "import { getSession } from
   '@/lib/auth/session'" in a client file will fail at build time.

7) Did NOT install @auth/prisma-adapter. The PRD says "через Prisma
   adapter ИЛИ ручная upsert в signIn" — the manual-upsert path is
   simpler (no extra dep, JWT strategy doesn't need adapter session
   tables, and we want explicit control over UserSettings creation).
   This means the adapter's accounts/sessions Prisma models are NOT in
   the schema and don't need to be — JWT-only mode works without them.

8) NEXTAUTH_URL=http://localhost:3000 in .env.local. Auth.js v5 will
   resolve the OAuth callback URL to
   http://localhost:3000/api/auth/callback/google, which the user must
   register in Google Cloud Console (and add the production callback
   when deploying). No code change needed — this is a Cloud Console
   config the user owns.

9) Auth.js v5 also auto-recognizes AUTH_SECRET / AUTH_URL aliases, but
   since TASK-003's zod schema standardized on the NEXTAUTH_* names, I
   pass env.NEXTAUTH_SECRET explicitly to NextAuth({secret}) so no
   implicit env-var-name reliance creeps in. Behavior is identical;
   reading is more obvious.

DESIGN DECISIONS WORTH FLAGGING
-------------------------------
1) STRUCTURAL: revalidatePath calls happen AFTER the try/catch
   around the mutation, NOT inside it. Reason: if revalidatePath
   throws (e.g., misconfigured cacheComponents in the future, a
   Next internals bug, or test environments without a request
   context), that should NOT surface as a mutation failure
   to the caller. The DB write already succeeded; reporting
   {success:false} would mislead the form into showing an
   error toast and the user into thinking they need to retry.

   Shape:
     mutate → try/catch
       on failure: return {success:false, error}
     (try block exits)
     revalidateChallengeViews()   ← outside catch
     return {success:true, data}

   This bug was caught during smoke-test development: the
   first version had revalidatePath inside the try, and the
   first 4 test cases (valid create / valid update / strip
   fields / valid delete) all returned success:false with
   error="Invariant: static generation store missing in
   revalidatePath /challenges" — the DB writes succeeded but
   the revalidate threw and got swallowed as a mutation error.
   Restructure fixed it; the 5 already-failing-before-revalidate
   tests (zod errors, IDOR, etc.) still pass because they
   never reach the revalidate call.

2) UN-AUTHED PATH: requireSession() in lib/auth/session.ts
   calls auth() then redirect('/login') from next/navigation
   when session.user.id is missing. redirect() throws
   NEXT_REDIRECT (a control-flow exception). For server
   actions invoked via the React server-action POST, Next.js
   catches NEXT_REDIRECT and turns it into a 307 response —
   the user lands at /login. That IS the "throws unauthorized"
   behavior required by test_step 2.

   I deliberately did NOT add a defensive
   `if (!session) return {success:false, error:'Unauthorized'}`
   guard — that would be unreachable code (requireSession
   never returns when session is missing) and would mask the
   real UX which is "redirect, not stay-on-page-with-error".

3) ACTION SIGNATURE: actions take `input: unknown` and
   safeParse with the existing schemas from TASK-010. The
   alternative — taking FormData and extracting per-field —
   was rejected because:
     * react-hook-form (already a dep) submits typed objects,
       not FormData, so the form pattern in TASK-014 wants
       object input
     * z.coerce.date() in createChallengeSchema handles ISO
       date strings from <input type=date> directly
     * Separating object-vs-FormData would require two
       parallel action variants — premature abstraction

4) ERROR FORMATTING: formatZodError joins all issues with
   '; ' so a form can show every problem at once via a single
   toast. Issue path falls back to "input" for refine-level
   errors that have an empty path. If a future task wants
   field-level errors (e.g., setError per path), that's a
   contract change — would expand the result to include
   issue list, not a string. Doesn't block TASK-014.

5) revalidateChallengeViews() always revalidates /challenges
   AND /dashboard (per acceptance criterion 5). Additionally
   revalidates /challenges/[id] for create + update so the
   detail page (TASK-032) sees fresh data. Delete revalidates
   only the list views — the detail page will 404 after
   delete anyway.

   directive 'no premature abstraction' is respected

   for extraction was already crossed) and the abstraction
   is minimal — just data + a 1-line helper function.

2) PREFIX-MATCH ACTIVE DETECTION: isNavActive returns
   true for exact match OR href + '/' prefix. This means

   the 'Челленджи' tab highlighted, ready for TASK-014
   and TASK-015. Exact-match-only would have failed there.

3) usePathname() ?? "": Per the Next docs, app-router
   usePathname always returns a string, but the null
   guard is cheap defense in case Next 16 introduces
   transient nullness during cacheComponents Suspense
   boundaries (the docs warn this scenario may need a
   Suspense boundary for dynamic-param routes). Falsy
   isNavActive on the empty-string pathname just means
   nothing is highlighted, which is the right fallback.

   lg:hidden, Sidebar uses hidden lg:flex. The mutual
   exclusion is enforced by the Tailwind class system
   at the breakpoint boundary (lg=1024px), no runtime
   branching, no hydration mismatch risk. Both components
   render to the DOM but only one is display:flex/grid

What I changed:
- beatyourself/app/(app)/dashboard/page.tsx

      trigger={
        <Button size="lg" className="w-full text-base">

      }
    />
    Full-width Button (size=lg, w-full) keeps thumb reach on mobile and stretches
    gracefully on desktop. ActivityForm (TASK-018) already handles the responsive
    Sheet (mobile) vs. Dialog (desktop) split internally — no new modal logic here.
    Trigger uses lucide Plus icon, matches the iconography elsewhere in the app.

- beatyourself/app/(app)/layout.tsx
    Mounted <Toaster/> (from components/ui/sonner.tsx) as a sibling of {children}.
    This is the prereq deferred from TASK-002/TASK-007/TASK-018 progress notes
    ("the Toaster from components/ui/sonner.tsx should be mounted in the (app) layout").
    Placed in the (app) layout (NOT root) so /login stays minimal. Without this mount
    the toast.success/error calls in ActivityFormFields would be no-ops, defeating
    the visual confirmation half of test_step 2.

Why no extra plumbing for "streak increments / challenges progress updates":
- createActivityAction (actions/activities.ts:22-25) already calls
  revalidatePath('/dashboard') + revalidatePath('/challenges') after a successful
  create.
- Next 16's revalidatePath invalidates the route's cached render, so on the next
  navigation/re-render the DashboardPage server component runs getDashboardData()
  fresh, which re-invokes calculateStreak (TASK-021) over the new activity row.
- createActivity in lib/services/activities.ts also calls
  recalculateChallengeProgress (TASK-019), which updates Challenge.currentValue —
  ActiveChallengesList re-renders with the new value.
- Net: no dashboard-page changes needed beyond inserting the trigger button.

Test_steps coverage (per PRD acceptance):
1. Click the button → form opens.
   ActivityForm wraps trigger in SheetTrigger asChild (mobile) / DialogTrigger asChild
   (desktop) — existing TASK-018 wiring. Click sets open=true.
2. Save → form closes, streak increments if was inactive, challenge progress updates.
   onSubmit awaits createActivityAction → on success calls onSuccess →
   handleSuccess sets open=false (TASK-018). revalidatePath('/dashboard') is in
   actions/activities.ts. Next render hits getDashboardData() fresh → streak +
   challenges reflect the new row.
